# Лекція · Загальна архітектура (модуль 00)

Мета sandbox: **mock crypto PSP** — приймає намір (invoice), підтверджує факт (captured), повідомляє мерчанта, усе в Docker.

## Хто з ким говорить

```text
Людина (ти)
    │
    ▼
┌─────────────┐      HTTPS       ┌──────────────────┐
│  Desk UI    │ ───────────────▶ │  API (Nest)      │
│  React      │                  │  команди + читати │
└─────────────┘                  └────────┬─────────┘
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ▼                     ▼                     ▼
              ┌──────────┐         ┌──────────┐          ┌────────────┐
              │ Postgres │         │ RabbitMQ │          │ Mock rail  │
              │ факти    │         │ події    │          │ on/off-ramp│
              └──────────┘         └────┬─────┘          └────────────┘
                                        │
                                        ▼
                                  ┌──────────┐      HTTPS
                                  │ Worker   │ ──────────▶ Merchant
                                  │ webhooks │              callback
                                  └──────────┘
```

## Чотири ролі (запам’ятай так)

| Роль | Відповідальність | Не робить |
|---|---|---|
| **Desk UI** | Кнопки: створити invoice, capture/fail, подивитись статуси | Не пише «баланс», не шле webhook, не тримає секрет підпису |
| **API** | Приймає команди, валідує, пише стан у DB, публікує подію | Не чекає відповіді мерчанта |
| **Postgres** | Джерело правди по invoice / статусах / delivery log | Не бізнес-логіка |
| **Broker + Worker** | Асинхронні наслідки (webhook, expire job) | Не вирішує «чи captured» — лише виконує наслідки після факту |

**Mock rail** — заглушка «банк/блокчейн сказав так/ні». У проді це був би реальний PSP/chain; у нас — кнопка або внутрішній сервіс.

## Головний інваріант продукту

> UI і зовнішні клієнти **не** є книгою. Статус invoice змінює лише API за правилами state machine. Повідомлення мерчанту — окремий контур.

## Що тече в системі (happy path)

1. Desk → API: створити invoice → DB `created` (TAKE)
2. Desk/API → mock rail → API ставить `pending` / потім `captured` (FILL)
3. API → RabbitMQ: «статус змінився»
4. Worker → merchant callback
5. Desk читає статус і лог доставок з API (GET)

## Docker Compose (логічно)

Один `docker compose up` піднімає:

- `web` — UI  
- `api` — Nest  
- `worker` — consumers (може бути той самий образ, інша команда)  
- `postgres`  
- `rabbitmq`  

Логи — JSON з усіх сервісів з `request_id` / `invoice_id`.
